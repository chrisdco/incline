# Tech decisions — storage & lists
Short-lived alternatives log. Revisit only when a trigger below fires; otherwise keep current stack.

## 1. KV: SQLite `kv` table (not MMKV)

- **Decision:** keep `src/db/kv.ts` (`kvStorage` over `expo-sqlite`) as the sole persist layer for Zustand (`settings-store.ts`, `active-workout-store.ts`), readiness, plan/deload snooze, sync cursors (`ACCOUNT_PREFS_UPDATED_AT_KEY`, `ACTIVE_PROGRAM_KEY`), narrate cache. `expo-secure-store` stays only for Clerk tokens (`src/auth/secure-store.ts`).
- **Why:** single source of truth, transactional with workout data, trivial account-switch wipe + backup/restore, works in Expo Go, zero extra native deps, testable with `better-sqlite3` in vitest. Current payloads are small + low-frequency; async Zustand persist is fine.
- **Why not MMKV:** sync/fast but native-only → breaks Expo Go (needs dev-client/prebuild). Splits persistence in two, complicates sync wipe + restore, needs migration for no measured gain. Same for AsyncStorage (deprecated path per `expo-upgrade`; `expo-sqlite/localStorage` would be the replacement, still not needed).
- **Revisit when:** (a) measured jank from async kv on hot path (e.g. rest-timer tick, 60fps reads), (b) Reanimated worklet needs sync reads, (c) startup trace shows kv as bottleneck via `eas-observe`.
- **If revisited:** use MMKV for ephemeral UI prefs only; keep sync-related keys (`user_preferences`, active program, outbox cursors) in SQLite. Migrate one key at a time with dual-read + backfill, keep `kvStorage` interface shape so Zustand `createJSONStorage` swap is one line. Requires dev-client + EAS build verification; document Expo Go break.

## 2. Lists: FlashList (not LegendList)

- **Decision:** keep `@shopify/flash-list 2.0.2` for `exercises`, `workouts`, `progress` history, `exercise-picker-sheet`, `photo-picker-sheet`. Keep `FlatList` for small fixed lists (calendar, day, share pager) and `react-native-draggable-flatlist` for template reorder (LegendList cannot replace drag).
- **Why:** curated + `inExpoGo: true`, recycling on by default, quirks already paid for (`use-data.ts` keep-prior-rows, sheets mounted outside FlashList in `progress.tsx`). Current lists are <500 rows paginated; no perf complaint.
- **Why not LegendList now:** wins are variable-height blanks, lower CPU/memory on fast flings, `maintainVisibleContentPosition` / `maintainScrollAtEnd`, bidirectional infinite, no-invert chat. None are triggered yet. Costs: second list system, `recycleItems` opt-in to match FlashList perf (same state-reuse pitfalls), community churn (v2→v3) vs Expo-curated support.
- **Revisit when:** (a) history/feed shows blanks or scroll jump on variable heights, (b) chat coach lands (needs maintain-end, no-invert), (c) social feed #78 (prepend + maintain position), (d) catalog grows 10x with images.
- **If revisited:** spike on Progress history only: rename to `LegendList` + `recycleItems`, compare with Perf Monitor / FlashLight on a mid-tier Android, check `@expo/ui` sheet nesting + `onEndReached` parity. Keep `FlatList` for tiny lists, draggable list as-is. Both lists work in Expo Go, so Go is not a decider here.

## 3. Dev auth bypass (not MMKV/FlashList-related — recorded here)

- **Decision:** `EXPO_PUBLIC_DEV_BYPASS_AUTH=1` + dev bundle signs in as fake local user `dev` with no token (`src/auth/use-app-auth.ts`, gated by `isDevAuthBypassEnabled()` in `src/lib/env.ts`). All app code uses `useAppAuth()` instead of Clerk's `useAuth`.
- **Prod safety:** the flag requires `__DEV__` (false + dead-code-eliminated in release); a set flag in a prod bundle logs a warning and is ignored. Bypass path ships no credentials and makes no network calls — sync/narrate fall into their existing unauthenticated null-paths, and sync is explicitly disabled in `use-cloud-sync.ts`.
- **Dev-testing safety:** bypass data is throwaway — `bindLocalAccount('dev')` claims the DB owner, so signing in with a real account later wipes it via the normal account-switch path (`src/db/account.ts`). Sign-out row is hidden in bypass to avoid a confusing bounce.
- **Revisit when:** never for removal rationale — keep indefinitely as a dev tool. Extend only if new `useAuth` call sites appear (grep `@clerk/expo` — only `(auth)/` screens should import it directly).

## 4. Set types: working / warmup / drop / failure

- **Decision:** `SetType` expanded beyond `working | warmup` (`src/db/types.ts`). Rule: only pure `working` drives PR/overload/ghost records ("back-offs cannot win", extending the warm-up rule); `drop`/`failure` count toward volume like working, carry RPE, and sync as raw `TEXT` (server column unconstrained). No migration needed.
- **UI:** set number is a button opening a 4-option sheet (`SetRow` → `ExerciseBlock` menu); non-working sets show a W/D/F tag under the number. Tap-to-complete, keyboard chain, and swipe-delete unchanged.
- **Revisit when:** Track B (#126 volume definition) may re-scope whether drop/failure belong in working volume — that decision owns this one.

## 5. Session loading: split cheap rows from assist fan-out

- **Decision:** `load()` split into `loadSession()` (rows only) + `loadAssist()` (last-sets/PR/suggestions/ghost, run-guarded against stale responses). Field edits never touch assist; structural changes (add/undo) use `reloadAll()`. Failure paths still reload from SQLite truth.
- **Why:** assist data cannot change on a keystroke; refiring it per edit was the wasteful half of session jank. No new architecture — write-through state + targeted invalidation approximates what native reactive stores do (see §6).
- **Revisit when:** only if session open itself feels slow (then: defer ghost/suggestions below the fold, not a store rewrite).

## 6. What native competitors do (Hevy / Lyfta / Strong) and our scope

- **Their stack (informed inference — none publish it):** fully native iOS + Android codebases, local DB as truth (Core Data / Room / Realm) with reactive observation (diffed, surgical UI updates — never refetch-on-edit), synchronous write-through transactions, background sync operation queues, release builds only, teams of 10–30 with years of perf iteration. Lyfta's tag set (Warm Up, Failure, Drop, Negative, Left/Right) matches our 4 types; Negative/L-R are easy later additions (`isSetType` passthrough + TEXT column already allow it).
- **The gap you feel is three stacked things:** (a) dev-vs-release — Expo Go dev is unminified, unoptimized JS; their apps are release native. This alone dwarfs architecture. (b) Reactive-native vs our RN bridge (narrowing: New Architecture + write-through already converge the UX). (c) Polish backlog (memoization where measured, list tuning).
- **Justification for our scope:** solo/small team, one cross-platform codebase, pre-alpha proving sync correctness. Nothing above requires a rewrite: expo-sqlite + write-through + split loads is the same UX contract as their reactive stores. WatermelonDB/Realm would need native modules (breaks Expo Go) for no user-visible gain.
- **Merge later, only if measured:** normalized reactive mirror, Skia charts, release-build perf discipline (dev-client profiling before any perf claim).

## 7. Session reopen: stale-while-revalidate, not remount-and-spinner

- **Decision:** in-memory session cache (originally `src/db/session-cache.ts`, cap 5; since §11 the QueryClient entry behind `getCachedSession` in `src/lib/query-keys.ts`, 30 min gc). Reopen renders cached rows synchronously + refreshes in background; tray/resume pushes warm it first (`setCachedSession` sync where the object is held, `getWorkoutLog` fire-and-forget from the tray). True cold opens show a layout-matching skeleton, never a bare spinner.
- **Safety:** single-writer; `resetUserData()` clears the cache (now `queryClient.clear()`) (ids restart after wipe, so stale entries could otherwise cross accounts); finish/discard drop their entry.
- **Rule for elsewhere:** same treatment when a push-then-back flow flashes — cache + warm + skeleton. Do not hand-roll JS transitions; the native Stack push is already the cheapest animation. Candidates if reported: workout preview, exercise detail, summary.

## 8. Touch + gesture rules learned (tray, swipe, home hero)

- **Tray:** whole bar opens, only the trash circle deletes; feedback is opacity (works on iOS too — `android_ripple` is Android-only, so iOS taps felt dead).
- **Swipe over inputs:** `TextInput` must come from `react-native-gesture-handler`, not `react-native` — native inputs eat the swipe gesture on Android. Set-type sheet also carries Delete as a discoverable fallback.
- **Home hero:** skeletons gate on `loading && data == null`, never `loading` alone — focus refetches must not flash placeholders over content. Same rule anywhere `useAsync` preserves data.

## 9. Android widgets: display-only, platform-split, refresh at write sites

- **Decision:** two fixed-size Jetpack Compose widgets via `expo-widgets` + `@expo/ui` — `NextUp` 4×2 (in-progress / today / suggested / ready, plus weekly progress and streak) and `ThisWeek` 2×2 (sessions vs goal). `resizeMode: "none"`, `updatePeriodMillis=0`. Android-only: `enablePushNotifications` is deliberately omitted so the plugin skips the iOS target (it throws without `ios.bundleIdentifier`).
- **Why display-only:** expo-widgets Android has no tap-to-open action (widget buttons only broadcast prop updates), so we ship no fake CTA. Copy says what to train; opening the app stays the launcher icon's job.
- **Platform split:** `src/lib/widgets/refresh.ts` is a no-op; the implementation is `refresh.android.ts`, so Metro keeps the widget runtime and `@expo/ui/jetpack-compose` out of iOS/web bundles (verified in exported Hermes bytecode).
- **Data:** pure `buildNextUpProps` / `buildThisWeekProps` own all copy/formatting and are unit-tested. Both light and dark palettes arrive in props because Android's `environment` only carries `colorScheme`; the `Updated` stamp is absolute because widgets cannot recompute a relative label.
- **Refresh:** app mount/foreground (30 s throttle), the SQLite table-change event for the tables the snapshot reads (1 s trailing debounce — covers start/finish/discard/delete and sync pulls), and accent/weekly-goal settings changes. Write sites never call it. Never a timer; SQLite stays the source of truth.
- **Revisit when:** expo-widgets ships tap-to-open/deep links → add a real CTA; or a third surface is proposed → keep one job per widget instead of growing `NextUp`.

## 10. Rest alerts: exact alarms, foregrounded +1 min

- **Decision:** `rest_complete` uses a wall-clock DATE trigger with `delivery: 'alarmClock'` and declares `SCHEDULE_EXACT_ALARM`. The channel is HIGH importance, lock-screen `PUBLIC`, no badge.
- **Why:** rest is time-critical. Inexact delivery defers under Doze and lands after the set; `alarmClock` is the documented user-visible alarm path. Android 12–13 grant exact alarms by default; Android 14+ denies them until the user allows "Alarms & reminders", so Settings shows a "Precise rest alerts" grant row while rest alerts are on and the grant is missing.
- **+1 min:** foregrounds the app (`opensAppToForeground: true`) and deep-links to `/session/:id`; `rest-timer-signal` restarts the in-app countdown, including cold start. Background actions are only delivered while the process is alive, which is exactly when the old dead-button behavior hurt. Skip stays background (nothing to re-arm).
- **Dedupe:** notification responses key on request id **plus delivery date**, so a re-fired alert is handled again while a cold-start replay of the same delivery is ignored.
- **Revisit when:** expo-widgets' Android custom-notification API can host a live countdown → move the countdown out of the notification body; or an OEM still defers `alarmClock` → document the per-OEM battery setting instead of adding a timer.

## 11. Reads: TanStack Query, invalidated by table (2026-10-26)

- **Decision:** `@tanstack/react-query` replaces the hand-rolled `useAsync`, `exercise-cache.ts` and `session-cache.ts` (adopted ahead of the "five caches" trigger in #228). One `QueryClient` (`src/lib/query-client.ts`): `staleTime: Infinity`, `networkMode: 'always'`, `retry: false`.
- **Keys start with the tables read** (`dbKey(TABLES.logs, 'workoutLog', id)`; groups in `src/lib/query-keys.ts`). The table-change event (`src/db/changes.ts` — post-commit from `mutate()`, plus expo-sqlite's update hook for everything else) invalidates every query whose key names a changed table. No `useFocusEffect` refetches, no invalidation calls at write sites, never a timer.
- **Focus-gated:** `use-data` hooks pass `subscribed: useIsFocused()`. Tabs stay mounted under the session stack; without the gate every set edit would refetch Home behind the session screen. Stale queries refetch on refocus.
- **Cached-first, no spinner regressions:** `placeholderData: keepPreviousData`; hooks keep the `{ data, loading, error, refetch }` shape so the §8 skeleton rule (`loading && data == null`) is unchanged. The catalog query never GCs and is prefetched 2 s after launch; the live session entry is read/written via `getCachedSession` / `setCachedSession` and is never observed while the session screen owns it, so per-edit invalidation costs nothing.
- **Over-including a table is cheap** (one extra refetch on focus); missing one leaves a screen stale — err wide when adding a key.
- **Revisit when:** the session screen moves onto a query of its own (session-engine refactor) → give it a narrow key and optimistic `setQueryData` instead of local state.
- **Writes: every app write in `src/db/queries/` goes through `mutate()`** (`src/db/write.ts`, #141/#138): the row changes and their outbox enqueues share one BEGIN IMMEDIATE transaction and roll back together; enqueue failures propagate to the caller. Reads inside a write use the `tx`; helpers that write take it as a parameter (never nest `mutate()`). File I/O stays outside the transaction (photos: copy first, delete the copy if the DB write fails; deletes remove files only after commit). `resetUserData` is one transaction over every user table, the outbox and sync cursors, and still clears the `QueryClient` up front for both reset paths (Profile → reset, account switch).
- **Deliberate exceptions** (write on the shared connection, outside `mutate()`; covered by the update hook):
  - `src/sync/*` — pull apply, push bookkeeping (`removeOutbox`, `bumpOutboxAttempt`, quarantine), cursors/status, `photo_blob_queue`. `clearOutbox` / `resetSyncState` accept a `tx` so `resetUserData` can include them.
  - Seeding (`src/db/seed*`) and migrations — run before the app reads anything.
  - `src/db/kv.ts` (`kvStorage`, Zustand persistence) — UI/session state, no outbox. The active program is the one synced kv key: `programs.ts` writes it on the `mutate()` tx so the kv row and its outbox entry commit together.
  - `src/db/account.ts` owner claim in `schema_meta`.

## 12. Theme tokens: one TS source, generated `global.css` (2026-10-26)

- **Decision:** `src/styles/tokens.ts` holds every theme color: CSS variable channels (`BASE_VARS` for `:root`/`.dark`, `ACCENT_TOKENS[id].vars` for `theme-*` and the aurora skins), radius, and the native hex tables (`NATIVE_NEUTRALS`, accent `hex`, aurora `darkBackgroundHex`, `CHART_SUPPORT_HEX`, `PLACEHOLDER_HEX`) plus the pure `themeHex()`. `src/global.css` is **generated** from it by `buildGlobalCss()` (`src/styles/global-css.ts`). `lib/theme.ts`, `lib/accent-themes.ts`, `lib/icon-color.ts`, the widget palette and `PLACEHOLDER_COLOR` all read from it.
- **Workflow:** edit `tokens.ts`, run `pnpm tokens:css` (a vitest `toMatchFileSnapshot` run with `-u`). In CI the same test fails when `global.css` is stale, so it rides the existing `pnpm run test` step. There is no separate script or CI job.
- **Why a generator, not NativeWind `vars()` at the root View:** `vars()` puts the palette in a JS style object that css-interop re-applies on the root View at runtime, and it would have to be rebuilt for every scheme × accent switch. Static CSS keeps today's compile-time path: NativeWind resolves the `theme-*`/`.dark` classes the way it does now, web gets real CSS, and theming costs nothing at runtime. The generated file is byte-identical to the old hand-written one apart from a "generated" header.
- **Zero visual change, pinned:** `src/styles/__tests__/theme-tokens.test.ts` compares a baseline captured from main before the refactor (`__fixtures__/theme-baseline.json`) against the new code: resolved CSS colors via cascade for all 8 accents × 2 schemes, plus `themeHex`, chart palettes, icon colors, widget palettes and the accent table. An intentional palette change updates that fixture in the same PR.
- **Known drift kept as-is** (fixing any of it is a visible change, so it's left for the polish pass):
  - Native neutrals are pinned hex, not derived from the CSS channels. Native `muted` (`#e4e4e7` / `#3f3f46`) is closer to the CSS `border`/`input` grey than to CSS `muted`. Accent `hex` values are close to their HSL channels but not exact.
  - Aurora skins only swap the native dark `background`. Native `card`/`border`/`muted` and icon colors stay Classic under rose/electron, and light-mode aurora backgrounds aren't reflected natively at all.
  - `primaryForegroundChannels()` (icon `primary-foreground`) uses a lightness cut-off, so it disagrees with CSS `--primary-foreground` for some accents (e.g. indigo light gives dark ink in icons, white in CSS).
  - Auth screens use `#6b7280` placeholders instead of `PLACEHOLDER_COLOR` (`#71717a`).
- **Primitives:** `Text` and `Skeleton` now live with their semantic wrappers/presets in `components/common/text.tsx` and `components/common/skeleton.tsx`. `components/ui/text` and `ui/skeleton` are gone.
- **Revisit when:** the polish pass converges native hex onto the CSS channels. At that point derive `NATIVE_NEUTRALS` and accent `hex` from the channels (an hsl→hex helper already exists in the test) and drop the pinned tables.
## 13. Sync protocol: batched server-side LWW push, per-table pull cursors (2026-10-26)

- **Decision:** push goes through one Postgres function, `sync_push(p_table, p_ops)` (`supabase/sync-schema.sql`), called once per table chunk of 100 outbox rows in `PUSH_ORDER` (`src/sync/push.ts`). Last-write-wins is decided in the write statement itself: `INSERT … ON CONFLICT (pk) DO UPDATE … WHERE excluded.updated_at > t.updated_at`. Deletes are tombstone-only `UPDATE … WHERE r.updated_at > t.updated_at`. Each op comes back `applied` / `stale` / `absent` / `error`.
- **Why one generic function, not one per table:** the column list comes from `pg_attribute` filtered to the keys the client sent, so a new cloud column needs no SQL change, only a mapper change. A whitelist maps table → primary key (`id`, or `user_id` for the singletons). `SECURITY INVOKER` keeps RLS in force, and `user_id` is forced to the JWT `sub`. Each op runs in its own `BEGIN … EXCEPTION` block, so a bad row (FK, cast, RLS) reports `error` without rolling back the rest of the chunk.
- **Singletons:** `profiles` keeps the "never clobber a named cloud profile with an empty placeholder" rule as an extra conflict predicate (refused writes report `stale` and are acked, as before). Clearing `user_active_program` is a null upsert plus tombstone, so it lands even with no cloud row. `user_preferences` is a plain jsonb upsert. All three are mapped in `buildPushOp` (`src/sync/mappers.ts`), which stays the only mapping layer.
- **Ack / retry / quarantine (#139):** applied, stale and absent are acked with `removeOutbox(item)`, which matches op + payload + created_at, so an edit that coalesced in mid-push survives. `error`, an unreported row, or an unreadable payload bumps attempts with the same match, so a fresh edit never inherits the old failure. At 8 attempts a row is quarantined: skipped by the keyset push query, it never blocks other rows, it shows in `lastError` as "N changes could not upload", and it is released by the next local edit (`enqueueSync` resets attempts). Rows for unknown tables are quarantined straight away.
- **Auth (#201):** `getSyncClient` decodes the JWT locally before any network call. It needs `aud` to contain `authenticated` (JWT template) or `role: authenticated` (Clerk native integration), a future `exp`, and `sub` equal to the signed-in user. A failure stops the run with a clear `lastError` and touches no attempts. Server-side 401/403, `PGRST30x`, `28000` and `42501` at call level do the same. A transport or 5xx failure stops the run without bumping either, so a bad network never poisons rows.
- **Pull (#140):** each table keeps its own `(updated_at, id)` cursor in `schema_meta` (`sync_cursor:<table>`). It stores the server's own timestamp string, so microsecond values cannot re-match forever. Pages of 500 are read until a short page. Each page is applied in one `withTransactionAsync`, and the cursor is saved after each page, so a kill mid-restore resumes from the last whole page. A blocked child no longer pins the cursor: it is parked in the cursor's `retry` set, re-fetched by id on later runs, and dropped with a warning after 5 tries. The old shared ms cursor seeds every table once (inclusive `>=`) and is then deleted, so a table added later starts from zero.
- **Still device-clock LWW (#143):** the winner is the higher client `updated_at`; ties keep the incumbent, deterministically. The read-then-write race is gone, but clock skew can still pick the "wrong" device, and the merge is whole-row, not per-field. Server-assigned timestamps or a field-level merge are the next step if the two-device matrix shows real losses.
- **Known limit:** `withTransactionAsync` is not exclusive in expo-sqlite, so a UI write that lands during a pull page joins that transaction (the deferred "Tx-read interleaving note"). The page is small and rollbacks are rare. Revisit with the transactional write helper.
- **Deploy order:** run `supabase/sync-schema.sql` (idempotent) before shipping a build with this engine. An older server answers `PGRST202`, which surfaces as "Sync server is out of date" and does not bump attempts.
- **Revisit when:** a chunk regularly hits the PostgREST body limit (lower `PUSH_CHUNK`), quarantine counts show up in the field (add a dead-letter view to Settings), or the matrix shows skew losses (server timestamps).

## 14. Session engine: one zustand store + controller for the live session (2026-10-26)

- **Decision:** all live-workout state moves out of `src/app/session/[id].tsx` into `src/features/session/` — `engine.ts` (`createSessionEngine(deps)`, a vanilla zustand store plus methods) and `index.ts` (the app instance wired to the real queries, plus `useSessionEngine(selector)`). The store holds the rows, assist maps (last sets / PR / suggestions / ghost), rest per exercise, rest kind, pause, notes draft, the undo stack and the finish/discard flags. The screen only selects slices and calls engine methods. Toast, rest start/stop and the PR haptic are UI side effects the screen binds with `engine.bindUi()` while mounted.
- **Why a store, not a query:** the rows are edited optimistically many times a second, and a query keyed on `set_entries` would refetch on every edit (§11). The engine owns the in-progress copy and writes it to the reopen cache (`setCachedSession`). SQLite stays the truth: every row write still goes through the `mutate()` calls in `sessions.ts`, failures toast and reload rows, and nothing writes through a cache. Track A (lock-screen rest / Live Activity) reads this one store.
- **Persisted volatile state:** pause (`pausedAt`, `totalPausedMs`), rest per exercise and the notes draft go to kv under `session:<logId>:volatile` (#171, #156, #170). The payload carries the log's `started_at`. Ids restart after an account wipe, so a payload whose stamp does not match the open log is ignored. Writes are fire-and-forget (the notes draft is debounced 400 ms), and the entry is removed on finish or discard. Rest defaults fill only exercises without a saved value, for every session the engine opens (#168: seeding is part of `open(logId)`, so nothing is "first session only").
- **Pause vs rest:** pausing stops the workout clock and releases keep-awake. It does not pause the rest countdown. Rest is a wall-clock alarm (§10), so a paused workout still alerts when rest ends.
- **Write ordering:** each set has its own promise chain (#164). Rapid toggles, field edits and a delete on the same set commit in tap order, while different sets stay concurrent. `finish()` / `discard()` flush the chains first.
- **Undo:** a capped stack (10). Each set or exercise removal gets its own entry, and its snackbar's Undo restores exactly that entry (#167). The old single-slot pill is gone; the undo goes through the toast system (#213).
- **Finish / discard:** both are guarded synchronously by an in-flight promise, so a second tap joins the first instead of closing twice (#142). Finish refuses a workout with no completed sets: the dialog explains and disables "Finish & save" (#172).
- **Bottom dock:** `SessionDock` is the session screen's single bottom host, in layout flow. It holds the rest bar (`RestTimerBar docked`) and publishes `max(dock + safe area, keyboard) + 12` to `useToastInset`, so the global snackbar sits above the rest bar and above the keyboard (audit A14). Other screens keep the default tab-bar clearance.
- **Revisit when:** a second surface edits the live session (watch, widget actions), which would mean moving the engine's writes behind a command queue, or when per-set chains show up in profiles (coalesce queued patches).

## 15. Units: canonical kg/cm storage, convert at the edges (2026-10-27)

- **Decision (#136, #144):** every stored load (set weight, log `total_volume`, profile bodyweight, `bodyweight_entries`, PRs derived from them) is **kilograms**; every stored circumference is **centimetres**. Full REAL precision, never rounded on write. A unit is a *display* choice only. This is the "freeze storage, convert at render" option; converting stored history on every toggle was rejected (lossy repeated rounding, mass sync churn, and history that changes when a setting flips).
- **Why kg:** the catalog, coaching thresholds, the AI feature pack and every importer already assume metric; kg is the SI base and the most common unit across apps and gyms. Lb users lose nothing: 135 lb → 61.2349 kg → 135 lb round-trips exactly at the 2-decimal input precision.
- **One module:** `src/lib/units.ts` holds every conversion (`kgToDisplay`, `displayToKg`, `kgToInput`, `commitInputToKg`, `labelledToCanonical`, cm/in). Nothing else multiplies by 2.2046.
- **Edges:**
  - *Display:* `formatWeight` / `formatVolume` take canonical kg. Charts convert points first and use `formatDisplayWeight` / `formatDisplayVolume`, so axes are in the display unit.
  - *Input:* fields show `kgToInput` (2 decimals: 1.25 kg and 2.5 lb plates stay exact) and commit through `commitInputToKg`, which returns null when the shown number was not edited — a blur never rewrites stored kg with a rounded round trip or enqueues a sync row for nothing.
  - *Plate math* (`src/coaching/plates.ts`) is kg in / kg out, but increments and rounding happen in the display unit (+5 lb lands on 140, not on 2.5 kg shown as 5.5 lb).
  - *AI feature pack:* numbers are converted to `pack.unit` so the model and `narrate-validate` see what the user sees.
  - *Export:* CSV columns are `weight_kg` / `total_volume_kg`; body rows export kg/cm.
- **Legacy unit columns:** `workout_logs.unit` stays `'metric'` (now meaning "stored in kg"); `bodyweight_entries.unit` / `body_measurements.unit` are always written `'kg'` / `'cm'`. Readers still pass rows through `labelledToCanonical`, so a row synced from an older build is read correctly.
- **Backfill:** `src/db/canonical-units.ts` runs once per device inside `openDatabase()`: if the persisted global unit is imperial, set weights, log volumes and profile bodyweight are divided into kg; labelled 'lb'/'in' body rows are converted whatever the global unit. Converted rows get a fresh `updated_at` and an outbox entry. Server-only rows from the web importer: `supabase/units-canonical.sql` (one-time, idempotent). The web importer now always writes kg.
- **Known limit:** a device still on a pre-§15 build keeps writing pound numbers; every device must update. Pre-alpha, accepted.
- **Per-exercise unit:** an exercise may override the global display unit (`exercises.weight_unit`, NULL = follow global), switchable from the exercise menu mid-session. It changes display only, never stored values. Synced through account preferences keyed by the exercise's sync ref. Volume totals across exercises use the global unit.
- **Revisit when:** a bodyweight/assisted-load model lands (negative or added loads), or stones/other units are requested — both extend `units.ts`, not storage.
